**由答复推导出的四条硬约束**：

1. **准确的部分必须走标签**（角色名/身份/版权）—— 因为"角色可能认不出"是 LLM 的固有问题，

2. **语言模型不做主线** —— 小模型不规范、占空间、约束力弱、慢。
3. **性能是第一约束** —— 反推已经"占用时间太长影响生图"。
4. **自然语言仍要** —— 作为"标签不够充分"的补充，但不能牺牲 1–3。

              ┌─────────────────────┴─────────────────────┐
              ▼                                           ▼
    ┌───────────────────┐                     ┌────────────────────┐
    │ 过滤模块           │                     │ 扩写模块            │
    │ = 按分类剥离/保留  │                     │ = 生成后过词表校验   │

#### ★ 关键验证：自然语言可以零 LLM、微秒级、零幻觉地生成

原型的核心洞察：**Danbooru 标签本身就是英文短语**（`long hair` / `looking at viewer`），
所以拼装自然语言**不需要翻译、不需要生成**，只需要按语义分类套英文句式模板。
每个词汇都来自输入标签 → **结构上不可能幻觉**。
实测加载 50,110 条 official category 仅 **0.1 秒**，分类+拼装是纯字符串操作。

用你工作流里的**真实 WD14 输出**跑原型（脚本 `.scratch/proto_nl_writer.py`）：

```
IN : plana \(blue archive\), long hair, breasts, looking at viewer, silver hair,
     purple eyes, halo, school uniform, blush, smile, white background, standing,
     arms behind back

OUT: Plana from Blue Archive with long hair silver hair, purple eyes, halo,
     wearing school uniform standing, arms behind back, blush, smile,
     looking at viewer, in white background
```

**注意 `Plana from Blue Archive`** —— 角色名与出处**完全来自标签**，语言模型认不出的角色，
标签库是精确的。这正是你要的「角色、名字用原生正确标签，句子结构由模板提供」。

> 这个原型还很粗糙（多 hair 标签未合并、`hat` 正则误伤 `hatsune`、`closed eyes` 重复分类），
> 但它证明的是**可行性**：管线不需要任何模型，因此不受模型能力/显存/网络/费用的约束。
> 正式实现要做的打磨：形容词合并（`long silver hair`）、去重、句式平滑、长度闸门。

#### 定稿形态：一条主干 + 两个可选支路

```
输入：标签串（来自 WD14 / Packer / 你的任何反推源）
  │
  ├─① 分类（自有索引，微秒级）─────────────── 过滤模块同款地基
  │
  ├─② 标签补全（路线 C，微秒级，可关）
  │     查共现/蕴含表 → 只补「统计上强同现且属同类」的标签
  │     ⚠️ 必须可 diff：用户要能看见"补了哪些"
  │
  ├─③ 自然语言生成（零 LLM，微秒级，可关）
  │     按分类套英文模板 → 输出到**独立输出口**（不污染标签串）
  │
  ├─④ 可选：VLM 看图补标签（路线 B，秒级，默认关）
  │     只有它能补「图片里有但标签没有」的东西
  │     ⚠️ 输出必须过词表校验，非法 token 丢弃或降级
  │
  └─⑤ Anima 格式化层（微秒级，总是执行）
        下划线→空格 · artist 加 @ · 区段重排 · 长度闸门 · 词表校验
```

**为什么 ②③⑤ 是主干**：全部是纯查表/纯字符串，**总耗时在微秒到毫秒级**，
满足你「尽可能占用时间少」的硬约束，且零显存、零联网、零费用。

**④ 的取舍说明**：「补图片显示、danbooru 自带提示词却没有显示的东西」这个需求，
**只有看图才能做到**（纯文本模型无论如何看不到图片）。但 VLM 必然慢。
所以你已有 `RH_LLMAPI_NODE`（Qwen3-VL-8B）这条路 —— 建议把它做成**默认关闭的增强支路**，
需要时开；不需要时零成本。

## 4. UI 与向后兼容设计（已自行查清，不需要你决策）

### 4.1 UI：现有前端 widget 直接扩展即可，"节点太长"不是问题

`web/js/anima_danbooru_tag_getter_widget.js`（17KB，**已存在**）的做法是：
`hideNativeWidget()` 隐藏**全部**原生 widget，然后用 DOM 自绘面板：
- **两列网格**渲染分类开关 + 每个分类的权重输入框（12 个分类目前只占 **6 行**）
- 下方「排除」区：正则排除 / 精准排除 / 保留自然语言 / 过滤自然语言
- `computeSize = () => [0, 270]` 固定面板高度

**所以新增 8 个分类只是把网格从 6 行变 10 行**，把面板高度从 270 调到约 360 即可。
不需要新的控件类型、不需要折叠、不需要多选下拉。

### 4.2 ★ 兼容性陷阱：**细化分类必然改变现有工作流的输出**

这是本次改动**风险最高的一点**，必须显式处理。

现状：`kisaki (blue archive)`、`touhou`、`hatsune miku` 这类标签**全部躺在「未归类词」里**。
你的工作流「未归类词」= True，所以它们现在会被输出。

分类细化后，它们会移动到新的「角色身份词」/「作品版权词」。
**如果新分类默认 `False`，升级后角色名会从提示词里静默消失** —— 这是严重的破坏性变更。

**处理原则（三条）**：

| 原则 | 做法 |
|---|---|
| **不丢标签** | 新增分类的 BOOLEAN **默认 `True`** —— 保证升级后输出集合只增不减，不会静默吞掉角色名 |
| **不动旧位置** | 12 个原 BOOLEAN 在 `required` 里位置不变；新增的 8 个追加到 **`optional` 的最末尾**（12 个权重 FLOAT 之后）。ComfyUI 按名字查找 widget，位置在末尾 → 旧工作流前 29 个 `widgets_values` 完全不受影响 |
| **给预设而不是让用户手点 20 个开关** | 加「场景预设」下拉：如 `换角色（剥离角色身份/版权/画师）`、`换装（再剥离服饰）`、`仅保留骨架（只留动作/表情/镜头/背景）`、`清除干扰（剥离审查/水印/质量元）`。预设只改开关状态，不引入隐藏状态 |

**升级说明必须写清**：原先埋在「未归类词」里的角色词 / 画师词 / 物件词现在有了独立分类，
用户需要检查自己的分类开关（或直接用场景预设）。

### 4.3 索引的发布方式（我的建议）

倾向 **(c) 随包放压缩版 + 首次运行解压**：
- 索引实测规模：22.6 万标签 × (分类 + 官方 category + 频次 + 中文名 + 归一化键)，
  JSON 会很大，需要紧凑编码（分类用整数枚举、频次用变长整数、字符串池化）
- 目标：压缩后控制在 **3–6MB**，解压后首次加载 < 1 秒，之后走 pickle 缓存（复用现有 `tag_category_index.cache` 的机制）
- 这样既不像纯 JSON 那样撑大仓库，也不像"首次运行构建"那样让首图等待

**合规**：Packer（`RafealaSilva/ComfyUI-Danbooru-Tag-Sorter-Node`）是 **MIT License**。
其 xlsx 分类标注若用于生成索引属许可范围，但需**在索引文件与 NOTICE 中保留版权声明与出处**。
我们**不照搬它的 12 类映射** —— 分类体系是我们重新设计的（原 12 类 + 8 新类），它只作为构建时的语义参考之一。
