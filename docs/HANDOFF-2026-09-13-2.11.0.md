## 一、先回答：为什么是 2.11，不是 2.9

**一句话：2.9 早就发布过了，而且是通过版本号"跳过"的 —— 本项目是 2.4.0 → 2.5.0 → … → 2.9.0 连续递增，不是从 2.9 跳到 2.11。**

### 版本谱系（`git log --follow -- VERSION` 实证）

| 版本 | 日期 | 主题 | 提交 |
|---|---|---|---|
| 2.4.0 | 2026-09-10 | Outputs 回退瀑布流 / LoRA 哈希优化 | `ad7b7a0` |
| 2.5.0 → 2.5.1 | 2026-09-11 | 缩略图后端直出（`/anima/thumb`） | `ddcbc58` |
| 2.6.0 → 2.8.1 | 2026-09-11 | 元数据后端化、Krea 2 筛选、按底模筛选、civitai.red | `1c021b4`…`a6290b8` |
| **2.9.0** | 2026-09-12 | 画布拖动性能专项 + 批量 LoRA 触发词改造 + `_find_lora_path` 崩溃修复 | **`357bf1e`** |
| **2.10.0** | 2026-09-12 | **破坏性**：`TK 相机控制` 退役 → `TK 可动素体相机` | `6d9ec25` |
| **2.11.0** | 2026-09-13 | **本次**：画廊瀑布流/随机发现 + outputs 自动更新 + CI/测试分层 + Registry | `2e071ba` |

### 为什么"感觉"是 2.9 → 2.11

因为你看到 2.9 的地方（**README 顶部**）当时确实写着 2.9.0，而 `VERSION` 文件已经是 2.10.0 —— 那是**一次真实的版本漂移**：

- `357bf1e` 把 `VERSION` 升到 2.9.0，README 同步成 2.9.0 ✅
- `6d9ec25` 把 `VERSION` 升到 2.10.0，但 **README 忘了改**，仍停在 2.9.0 ❌

所以 2.10.0 那一次是"改了 VERSION 没改 README"。我接手后先把漂移修掉（README → 2.10.0），
本次会话的改动再按语义化版本升到 **2.11.0**。

### 为什么本次是 minor（2.10 → 2.11）而不是 patch 或 major

按语义化版本判断，本次改动是"**新增功能 + 修复 + 不含破坏性变更**"：

- **新增**（→ 必须升 minor）：画廊自适应张数、随机发现三档、真瀑布流、`/anima/gallery/fresh`、
  只读 CI、测试分层、Registry 元数据
- **修复**（→ 可 patch，但混在新增里随 minor 一起走）：order 计数槽、备份链、测试静默失效、CI
- **破坏性变更**：**没有** —— 节点 class name、API endpoint、工作流 JSON、IndexedDB、
  `prompt_library.json`、LoRA 分类、Outputs metadata 全部未动；画廊的"每页图片数"默认值变了，
  但**设置是每节点持久化的**，老用户已保存的 12/24/48 会继续沿用，不会被强改。
  （上一个真正的 breaking 是 2.10.0 的相机节点退役，那是 **major 语义**但因为项目
  `0.x`/`2.x` 阶段按"破坏性变更单独发一版 + CHANGELOG 顶部醒目标注"处理，未升 3.0.0。）

### ⚠️ 版本号的三个"口径"不要混

这是接手时最容易搞错的地方：

| 口径 | 值 | 说明 |
|---|---|---|
| **仓库版本（唯一真源）** | `VERSION` = **2.11.0** | `__init__.py` 运行时读它；README/CHANGELOG/pyproject 必须一致（`ai_verify` 强制） |
| **GitHub Release / tag** | **`v2.11.0` 与 `v2.10.0`** | **只有这两个** —— 2.9.0 及更早从未打过 tag（我这次才补建了 2.10.0） |
| **ComfyUI Registry 版本** | **2.11.0** | `NodeVersionStatusPending`，审核通过后公开可搜 |

**所以"2.9"确实存在过，只是它没有对应的 GitHub Release** —— 而 2.10.0 与 2.11.0 有。
如果你在 Release 列表里只看到 v2.10/v2.11，那是**补建的结果**，不是跳版。

## 六、接手必读的五个坑（都踩过并已固化）

1. **`pytest.ini` 必须在 `tests/` 里**，不能放仓库根。
   仓库根**就是** ComfyUI 插件的 `__init__.py`，pytest 会把它当包导入 → 全部 setup ERROR。
   **实测无效、别再试**：`import-mode=importlib`（pytest 9 的 ini 没这选项）、`pythonpath = .`、
   `collect_ignore`、`tests/__init__.py`、`--import-mode=append`。

2. **测试里 stub 模块必须"看着像包"**：`m.__path__ = []`，子模块挂到父模块属性上，
   否则 `from PIL import Image` 会在 import 机制里炸。且**只在真的缺失时 stub** ——
   用空模块覆盖真 `aiohttp` 不还原会污染同 session 后续测试
   （`conftest.py` 已有守卫会点名）。

3. **comfy-cli 在中文 Windows 上 GBK 崩溃**：`'gbk' codec can't decode byte 0xae`。
   用 `python -X utf8`。**且崩溃发生在"上传之后"** → 会以为失败其实已成功
   （重试报 `The node version already exists` 即证）。

4. **`comfy node publish` 报 `Failed to validate token` 有两个完全不同的原因**：
   ① PAT 是在"未登录账号"下生成的（registry 里查不到 user）；② PublisherId 含大写。
   别急着换 PAT，先跑 `python tools/registry_setup.py --token <PAT> --check` 区分。

5. **`web/` 是会被 ComfyUI 服务出去的目录** —— 任何 `.js` 备份都不能放里面，
   否则浏览器会把它当第二个扩展加载、`registerExtension` 跑两次（UI 重复注册）。
   备份一律放插件根目录（已在 `.gitignore` 忽略 `.workbuddy-bak-*/`、`_bak_*/`）。
